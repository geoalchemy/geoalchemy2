Spatial Indexes
===============

Spatial databases use spatial indexes to accelerate queries involving spatial operators and functions
(such as bounding-box intersections, distance queries, and geometric containment).

GeoAlchemy 2 simplifies spatial index management by automatically creating and managing spatial
indexes for :class:`~geoalchemy2.types.Geometry`, :class:`~geoalchemy2.types.Geography`, and
:class:`~geoalchemy2.types.Raster` columns.


Default Behavior
----------------

By default, any spatial column defined with ``spatial_index=True`` (the default) automatically
registers a spatial index in the table's metadata::

    from sqlalchemy import Column, Integer, MetaData, Table
    from geoalchemy2 import Geometry

    metadata = MetaData()
    lake_table = Table(
        "lake",
        metadata,
        Column("id", Integer, primary_key=True),
        Column("geom", Geometry("POLYGON")),
    )

The autogenerated index is assigned a default name using the template ``idx_<tablename>_<columnname>``::

    >>> [idx.name for idx in lake_table.indexes]
    ['idx_lake_geom']

When creating the table with ``lake_table.create(engine)`` or ``metadata.create_all(engine)``,
GeoAlchemy 2 automatically creates the corresponding spatial index using the native indexing mechanism
of the target database dialect.


Naming Conventions
------------------

SQLAlchemy allows you to define automated `constraint and index naming conventions
<https://docs.sqlalchemy.org/en/latest/core/constraints.html#constraint-naming-conventions>`_ on
:class:`~sqlalchemy.schema.MetaData`.

By default, GeoAlchemy 2 uses its hardcoded ``idx_<tablename>_<columnname>`` naming scheme for
backward compatibility. To instruct GeoAlchemy 2 to follow the naming convention configured on the
metadata, set ``follow_naming_convention=True`` on the spatial type.

SQLAlchemy Core
^^^^^^^^^^^^^^^

In SQLAlchemy Core, pass ``follow_naming_convention=True`` when defining the column::

    from sqlalchemy import Column, Integer, MetaData, Table
    from geoalchemy2 import Geometry

    metadata = MetaData(naming_convention={"ix": "ix_%(table_name)s_%(column_0_N_name)s"})
    lake_table = Table(
        "lake",
        metadata,
        Column("id", Integer, primary_key=True),
        Column("geom", Geometry("POLYGON", follow_naming_convention=True)),
    )

    >>> [idx.name for idx in lake_table.indexes]
    ['ix_lake_geom']

SQLAlchemy ORM
^^^^^^^^^^^^^^

In the SQLAlchemy ORM, associate the naming convention with the declarative base's metadata::

    from sqlalchemy import Column, Integer, MetaData
    from sqlalchemy.orm import declarative_base
    from geoalchemy2 import Geometry

    metadata = MetaData(naming_convention={"ix": "ix_%(table_name)s_%(column_0_N_name)s"})
    Base = declarative_base(metadata=metadata)

    class Lake(Base):
        __tablename__ = "lake"
        id = Column(Integer, primary_key=True)
        geom = Column(Geometry("POLYGON", follow_naming_convention=True))

    >>> [idx.name for idx in Lake.__table__.indexes]
    ['ix_lake_geom']

Or using the SQLAlchemy 2.0 ``DeclarativeBase`` class::

    from sqlalchemy import MetaData
    from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
    from geoalchemy2 import Geometry, WKBElement

    metadata = MetaData(naming_convention={"ix": "ix_%(table_name)s_%(column_0_N_name)s"})

    class Base(DeclarativeBase):
        metadata = metadata

    class Lake(Base):
        __tablename__ = "lake"
        id: Mapped[int] = mapped_column(primary_key=True)
        geom: Mapped[WKBElement] = mapped_column(Geometry("POLYGON", follow_naming_convention=True))

Resolution and Fallback Rules
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

When ``follow_naming_convention=True`` is enabled:

1. **Resolution**: The spatial index name is resolved using the ``"ix"`` key (or ``Index`` class key)
   defined in the metadata's naming convention dictionary.
2. **Fallback**: If the naming convention does not define an ``"ix"`` key (or if no naming convention
   is configured), the index name safely falls back to ``idx_<tablename>_<columnname>``.


Custom User-Defined Spatial Indexes
-----------------------------------

If you need full control over the spatial index (for example, to specify index storage parameters,
create a partial index with a ``WHERE`` clause, or index multiple columns), you should disable
automatic index generation by setting ``spatial_index=False`` and define an explicit
:class:`~sqlalchemy.schema.Index`::

    from sqlalchemy import Column, Index, Integer, MetaData, Table
    from geoalchemy2 import Geometry

    metadata = MetaData()
    lake_table = Table(
        "lake",
        metadata,
        Column("id", Integer, primary_key=True),
        Column("geom", Geometry("POLYGON", spatial_index=False)),
    )

    # Define a partial GiST spatial index on PostgreSQL
    Index(
        "idx_lake_active_geom",
        lake_table.c.geom,
        postgresql_using="gist",
        postgresql_where=lake_table.c.id > 100,
    )


Dialect-Specific Details
------------------------

PostgreSQL / PostGIS
^^^^^^^^^^^^^^^^^^^^

- PostGIS spatial indexes are created as GiST (Generalized Search Tree) indexes using
  ``USING gist``.
- **N-Dimensional Indexes**: By default, a 2D bounding-box index is created. For 3D or 4D geometries,
  you can set ``use_N_D_index=True`` on the spatial type to generate an N-D index using the
  ``gist_geometry_ops_nd`` operator class.
- **Managed Columns (`use_typmod=False`)**: When PostGIS type modifiers are disabled, columns are
  added via ``AddGeometryColumn()`` after table creation, and the spatial index is created in an
  ``after_create`` event using the resolved convention name.

MySQL and MariaDB
^^^^^^^^^^^^^^^^^

- Spatial indexes are created as ``SPATIAL INDEX``.
- **Default naming**: In MySQL, autogenerated spatial indexes are created unnamed by default
  (``ALTER TABLE <table> ADD SPATIAL INDEX (<column>)``), which causes MySQL to assign the column's
  name to the index.
- **Naming Conventions**: When ``follow_naming_convention=True`` is enabled, GeoAlchemy 2 explicitly
  names the index in the DDL statement (``ALTER TABLE <table> ADD SPATIAL INDEX <index_name> (<column>)``).

SQLite / SpatiaLite and GeoPackage
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

- SpatiaLite implements spatial indexing via R-tree virtual tables managed by C-extension functions
  (``CreateSpatialIndex`` / ``DisableSpatialIndex``).
- The names of these virtual tables and their internal triggers are fixed by SpatiaLite
  (``idx_<tablename>_<columnname>``). As a result, naming conventions cannot rename SpatiaLite R-tree
  virtual tables.
- GeoPackage likewise uses fixed R-tree virtual table names (``rtree_<tablename>_<columnname>``)
  managed via ``gpkgAddSpatialIndex``.

MSSQL
^^^^^

- SQL Server requires spatial indexes to be created with a bounding box and tessellation grid scheme
  (``GEOMETRY_GRID`` or ``GEOGRAPHY_GRID``).
- GeoAlchemy 2 automatically constructs and executes the required ``CREATE SPATIAL INDEX`` statement
  after the table is created, applying the resolved naming convention.


Using with Alembic Migrations
-----------------------------

When using Alembic for database migrations, autogenerated spatial indexes interact with Alembic's
autogenerate comparisons:

- Ensure you register :obj:`~geoalchemy2.alembic_helpers.writer` in your Alembic ``env.py`` to handle
  spatial index operations and suppress false diffs on SQLite/GeoPackage.
- When switching an existing database from default naming to ``follow_naming_convention=True``, Alembic
  will generate a migration to drop the old ``idx_<tablename>_<columnname>`` index and create the new
  convention-named index.

For detailed migration setup and examples, see :ref:`alembic_use`.
